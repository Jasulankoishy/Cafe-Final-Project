1. Introductory Part

1.1 Project Overview & Motivation

Modern food service systems require modular, extensible software to manage diverse menu categories, custom ingredient additions, fluctuating discount campaigns, and real-time synchronization between order intake, kitchen preparation, and cashier accounting.

The Cafe Ordering System is engineered as a clean-room demonstration of six classic Gang of Four (GoF) design patterns operating in complete harmony on Java 17. The system strictly avoids monolithic coupling by distributing creational, structural, and behavioral responsibilities into decoupled components.

3. Detailed Implementation of Design Patterns

3.1 Creational Patterns

Pattern 1: Builder (Implemented by Jasulan Koishybay)

Class: cafe.Order.Builder
Intent: Encapsulates the step-by-step assembly of an immutable Order record, enforcing non-null constraints, non-blank customer names, and requiring at least one item. 

public static class Builder {
    private final String customer;
    private final List<Item> items = new ArrayList<>();

    public Builder(String customer) {
        if (customer == null || customer.isBlank()) {
            throw new IllegalArgumentException("Customer name is required.");
        }
        this.customer = customer;
    }
    public Builder add(Item item) {
        items.add(Objects.requireNonNull(item));
        return this;
    }
    public Order build() {
        if (items.isEmpty()) throw new IllegalStateException("Add at least one item.");
        return new Order(customer, items);
    }
}

Pattern 2: Factory Method (Implemented by Adilet Ainadinov)

Classes: cafe.MenuItemFactory, cafe.BurgerFactory, cafe.TeaFactory
Intent: Defines an abstract creator method createItem() returning the Order.Item abstraction, allowing subclasses to decide the exact product and pricing details. 

public abstract class MenuItemFactory {
    public abstract Order.Item createItem();
}

public class BurgerFactory extends MenuItemFactory {
    @Override
    public Order.Item createItem() {
        return new Order.MenuItem("Burger", 1500);
    }
}

public class TeaFactory extends MenuItemFactory {
    @Override
    public Order.Item createItem() {
        return new Order.MenuItem("Tea", 500);
    }
}

3.2 Structural Patterns

Pattern 3: Facade (Implemented by Jasulan Koishybay)

Class: cafe.CafeFacade
Intent: Provides a single unified entry point placeOrder(...) concealing builder validation, strategy price computation, event publishing, and receipt generation. 

public Receipt placeOrder(String customer, List<Order.Item> items) {
    Order.Builder builder = new Order.Builder(customer);
    items.forEach(builder::add);
    Order order = builder.build();
    int total = pricing.total(order);
    Receipt receipt = new Receipt(order, total);
    events.placed(order, total);
    return receipt;
}

Pattern 4: Decorator (Implemented by Adilet Ainadinov)

Classes: cafe.ItemDecorator, cafe.CheeseExtra, cafe.BaconExtra
Intent: Dynamically augments any Order.Item with additional ingredients at runtime without modifying original classes or subclass proliferation. 

public abstract class ItemDecorator implements Order.Item {
    protected final Order.Item wrapped;
    public ItemDecorator(Order.Item wrapped) {
        this.wrapped = Objects.requireNonNull(wrapped);
    }
    @Override public String name() { return wrapped.name(); }
    @Override public int price() { return wrapped.price(); }
}

public final class CheeseExtra extends ItemDecorator {
    public CheeseExtra(Order.Item wrapped) { super(wrapped); }
    @Override public String name() { return wrapped.name() + " + Cheese"; }
    @Override public int price() { return wrapped.price() + 200; }
}

3.3 Behavioral Patterns

Pattern 5: Strategy (Implemented by Dias)

Classes: cafe.CafeFacade.Pricing, cafe.RegularPricing, cafe.DiscountPricing
Intent: Defines interchangeable calculation algorithms for order pricing. Guarded with long arithmetic and Math.floorDiv / Math.multiplyExact against integer overflow. 

public final class DiscountPricing implements CafeFacade.Pricing {
    private final int discountPercent;
    public DiscountPricing(int discountPercent) {
        if (discountPercent < 0 || discountPercent > 100)
            throw new IllegalArgumentException("Invalid discount percentage.");
        this.discountPercent = discountPercent;
    }
    @Override
    public int total(Order order) {
        long subtotal = order.items().stream().mapToLong(Order.Item::price).sum();
        long discounted = Math.floorDiv(Math.multiplyExact(subtotal, 100 - discountPercent), 100);
        return Math.toIntExact(discounted);
    }
}

Pattern 6: Observer (Implemented by Dias)

Classes: cafe.CafeFacade.OrderEvents, cafe.OrderEventPublisher, cafe.KitchenListener, cafe.CashierListener
Intent: Decouples event dispatching from department consumers (Kitchen prep and Cashier invoicing) using a publish-subscribe notification model. 

public final class OrderEventPublisher implements CafeFacade.OrderEvents {
    private final List<CafeFacade.OrderEvents> listeners = new ArrayList<>();
    public void subscribe(CafeFacade.OrderEvents listener) {
        listeners.add(Objects.requireNonNull(listener));
    }
    @Override
    public void placed(Order order, int total) {
        for (CafeFacade.OrderEvents listener : List.copyOf(listeners)) {
            listener.placed(order, total);
        }
    }
}

4. SOLID Principles Analysis

Principle Application in Project Architecture
Single Responsibility (SRP) Each class encapsulates one concern: Order.Builder for assembly, DiscountPricing for discounting, KitchenListener for food preparation notifications, CafeFacade for flow orchestration.
Open/Closed (OCP) Adding new toppings (e.g. PicklesExtra) or menu items (e.g. PizzaFactory) requires no modifications to existing classes.
Liskov Substitution (LSP) All decorators transparently substitute Order.Item. Both pricing implementations substitute Pricing identically.
Interface Segregation (ISP) Small, highly cohesive interfaces (Item, Pricing, OrderEvents) prevent clients from depending on methods they do not need.
Dependency Inversion (DIP) High-level CafeFacade relies exclusively on interface abstractions (Pricing, OrderEvents), never on concrete implementations.
